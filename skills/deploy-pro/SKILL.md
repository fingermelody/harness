# Deploy-Pro: 生产环境发布

## 概述

将代码从开发/测试分支合并到主干并部署到生产环境。严格遵循预检→合并→构建→部署→验证→回滚方案流程。

## 何时使用

- 用户需要发布到生产环境时**默认使用**
- 用户说「发布」「上线」「部署生产」「release」「go live」「上生产」
- 需要将测试通过的代码合并到主干并部署

**不使用此技能的场景：**
- 部署测试环境（使用 deploy-test-workflow）
- 纯代码编写（使用 basic-code-workflow）
- 仅合并代码不部署（直接用 git 命令）

---

## 前置条件

进入发布流程前，确认以下条件**全部满足**：

| 条件 | 确认方式 |
|------|----------|
| 测试环境已验证通过 | tester 输出 PASS 或 WARN（无 P0） |
| 代码 Review 已通过 | reviewer 输出 PASS |
| 质量评分≥80 | evaluator 输出评分 |
| 回滚方案已就绪 | 有明确的回滚策略 |
| PM 审批（如需） | 用户/PM 确认发布 |

**任一条件不满足 → 阻断发布，报告缺失项，等待用户决策。**

## 执行流程

### Step 1: 预检（Pre-flight Check）

**目标**：发布前全面检查，确保无遗漏。

**检查清单：**

```
□ 1. 分支状态
    - 当前分支：{branch}
    - 与主干差异：{commit count}
    - 未提交变更：{是否有 dirty files}

□ 2. 测试状态
    - 单元测试：通过/失败
    - 集成测试：通过/失败
    - E2E 测试：通过/失败
    - 覆盖率：{X}%

□ 3. 安全检查
    - 依赖漏洞扫描：无高危
    - 敏感信息泄露：无硬编码密钥/token
    - CHANGELOG/版本号：已更新

□ 4. 兼容性
    - 数据库迁移：向前兼容/需停机
    - API 变更：向后兼容/有破坏性变更
    - 配置变更：已同步到生产配置

□ 5. 回滚方案
    - 回滚方式：git revert / 重新部署上一版本
    - 数据库回滚：迁移回滚脚本已准备
    - 预计回滚时间：{X} 分钟
```

**预检结果**：
- ✅ 全部通过 → 进入 Step 2
- ❌ 有阻断项 → 停止发布，报告问题给用户

---

### Step 2: 代码合并（Merge）

**目标**：将代码合并到发布分支/主干。

**执行步骤：**

```bash
# 1. 切换到目标分支
git checkout {target_branch}  # 默认 main

# 2. 拉取最新代码
git pull origin {target_branch}

# 3. 合并源分支
git merge {source_branch}

# 4. 解决冲突（如有）
#    - 自动合并失败 → 列出冲突文件，询问用户处理方式
#    - 用户解决后继续

# 5. 打版本标签
git tag -a v{version} -m "release: v{version}"

# 6. 推送合并结果 + 标签
git push origin {target_branch} --tags
```

**版本号规则**：
- 补丁版本（Bug 修复）：`vX.Y.Z+1`
- 次版本（新功能）：`vX.Y+1.0`
- 主版本（破坏性变更）：`vX+1.0.0`
- 如用户未指定版本号，根据变更内容自动推断并确认

**合并失败处理**：
- 冲突 → 列出冲突文件，等待用户手动解决后继续
- CI 检查失败 → 报告失败原因，不继续部署

---

### Step 3: 构建（Build）

**目标**：构建生产环境产物。

**执行步骤：**

```bash
# 1. 安装依赖（生产依赖 only）
npm ci --production   # Node.js
# 或 pip install -r requirements.txt  # Python

# 2. 执行构建
npm run build         # Node.js
# 或 python setup.py build  # Python

# 3. 产物校验
#    - 构建产物大小是否合理
#    - source map 是否生成（调试用，不部署）
#    - 静态资源 hash 是否正确
```

**构建失败处理**：
- 报告构建错误日志
- 不继续部署，回退合并（如需）

---

### Step 4: 部署生产（Deploy）

**目标**：将构建产物部署到生产环境。

**执行方式**：使用 Agent 工具 spawn deployer agent。

**Deployer Prompt 模板：**

```
你是部署工程师，执行生产环境部署。

部署目标：生产环境
版本：v{version}
构建产物：{Step 3 输出路径}

执行步骤：
1. 读取生产环境配置（config.json 中的 environment_map.prod）
2. 执行部署：
   - K8s: kubectl set image / kubectl apply
   - Docker: docker-compose up -d --force-recreate
   - 静态资源: CDN 同步
3. 数据库迁移（如需）：
   - 执行迁移脚本
   - 验证迁移结果
4. 等待服务就绪（滚动更新完成）
5. 生产 Health Check：
   - 核心路由返回 200
   - API 健康检查端点
   - 关键业务流程可达

⚠️ 生产部署规范：
- 使用滚动更新，避免停机
- 逐个实例更新，保持可用性
- 部署后监控错误率 5 分钟
- 发现异常立即触发回滚
```

**部署结果**：
- ✅ Health Check 通过 → 进入 Step 5
- ❌ Health Check 失败 → 自动回滚到上一版本，报告错误

---

### Step 5: 验证（Verify）

**目标**：生产环境冒烟验证，确认关键功能正常。

**验证清单：**

```
□ 首页/主路由可访问 → 200
□ 登录/认证流程正常
□ 核心 API CRUD 操作正常
□ 新功能/修复点验证通过
□ 监控面板：错误率 < 阈值
□ 响应时间：P99 < SLA
□ 日志：无异常错误
```

**验证结果**：
- ✅ 全部通过 → 发布成功
- ❌ 有失败项 → 评估影响，决定回滚或热修复

---

### Step 6: 发布完成 & 回滚方案

**目标**：确认发布成功，保留回滚能力。

**回滚方案（记录备查）：**

```
回滚方式: git revert / 重新部署 v{上一版本}
回滚命令:
  git revert {merge_commit}
  git push origin main
  # 或: kubectl rollout undo deployment/{app}

数据库回滚:
  alembic downgrade -1  # Python
  # 或对应的迁移回滚脚本

预计回滚时间: {X} 分钟
```

## 流转规则

```
[用户发布需求]
    ↓
Step 1: 预检
    ├─ ✅ 通过 → Step 2
    └─ ❌ 阻断 → 停止，报告缺失项
    ↓
Step 2: 代码合并
    ├─ ✅ 合并成功 → Step 3
    ├─ ⚠️ 冲突 → 等待用户解决后继续
    └─ ❌ CI 失败 → 停止，报告失败原因
    ↓
Step 3: 构建
    ├─ ✅ 构建成功 → Step 4
    └─ ❌ 构建失败 → 停止，报告错误日志
    ↓
Step 4: 部署生产
    ├─ ✅ Health Check 通过 → Step 5
    └─ ❌ Health Check 失败 → 自动回滚，报告错误
    ↓
Step 5: 验证
    ├─ ✅ 全部通过 → Step 6
    └─ ❌ 有失败 → 评估影响，决定回滚或热修复
    ↓
Step 6: 发布完成 + 回滚方案记录 → ✅ 发布成功
```

## 注意事项

1. **预检不可跳过**：生产发布必须通过预检清单
2. **默认 main 分支**：合并目标默认为 main，用户可指定其他分支
3. **滚动更新**：生产部署必须使用滚动更新，避免停机
4. **自动回滚**：部署后 Health Check 失败自动回滚到上一版本
5. **数据库迁移需向前兼容**：新代码必须兼容旧数据库 schema，确保回滚后仍可用
6. **不自行修复**：部署失败时不自行修复代码，报告问题由用户决策
7. **版本号必须递增**：每次发布必须打新版本标签
